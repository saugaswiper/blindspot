# Brief 018 — Ranker latency: measured, warm-started, ≤300 ms/call at n = 3,000 (brief 017 scope 2 close-out)

**Priority:** NEXT
**Date:** 2026-11-09 (planner)
**Stage in pipeline:** Title/abstract screening, ML layer. Build order: unblocks brief 015 (full 22-review Set B benchmark), which precedes brief 016.
**Evidence:** handoff 137 and validation 016 §2E.
- Handoff 136 measured 340–450 ms/call at n ≈ 3,000, against a 300 ms target.
- Handoff 137 made `fit` faster with an exact change, but recorded no per-call ms and no warm-up split.
- The scorecard sweep covers 16 of 22 reviews (n ≤ 6,000, seed 1). The 6 larger reviews, up to n = 49k, are untested.
- No open FAIL is unaddressed. Validation 015's AC4 FAIL is answered by brief 017's stopping test, which fires 8/8 on ≥20-include reviews with true recall 1.0.

**Blockers:** none. SYNERGY is not in the dev cache, so the SYNERGY regression check uses the existing validation 015 harness. If the data is missing, say so in the handoff and use the Set B check below as the ranking guard.

## Goal
Make `rankRecords` fast enough for the full 22-review benchmark, and measure it honestly. This closes brief 017 AC3 and AC4 for scope (2) only. Brief 017's scope (1) stays as shipped.

## Why now
Brief 015's scorecard cannot be completed until the 6 larger reviews run in feasible time. Latency is the single remaining blocker, and it is currently unmeasured at the grain that matters (per call, after warm-up).

## Scope
**In** (one change: ranker latency)
1. **Measure first.** Add a timing mode to `scripts/benchmark-setb.ts`, for example `--timing`. It records per-call `rankRecords` ms, split into first call (cold) and calls 2…N (warm), at n ≈ 700, 3,000 and the largest Set B review. Commit the numbers to `spec/benchmarks/018-latency.json`.
2. **Profile and fix the dominant cost.** Candidates, in this order: per-call allocation in `fit`, scoring all n records each call, and the sort. Fix whichever the profile shows. Do not guess.
3. **Warm start.** Add `createRanker(records)` with `rank(verdicts)`. It reuses the memoised vectors and warm-starts the logistic weights from the previous round, with an early stop on loss change. `rankRecords(records, verdicts)` keeps its signature and behaviour.
4. **Class balance only if it helps.** Try weighting positives by `nNeg/nPos`. Keep it only if Set B WSS@95 does not drop (see the ranking guard in AC3). Otherwise leave it out and say so.

**Out**
- Stopping-rule changes, k-selection, UI, routes, and brief 015 conditions C/D/E.
- Any change to what the ranker outputs. It stays advisory.

## Files
`lib/screening-ranker.ts` (+ tests), `scripts/benchmark-setb.ts`, `spec/benchmarks/018-latency.json`, `spec/NNN-handoff.md`.

## Acceptance criteria (all `claimed` until the tester reruns; beat, don't match)
1. **Warm per-call latency:** median `rank` call at n = 3,000 is ≤ 300 ms, with p95 ≤ 450 ms. The bar to beat is 340–450 ms from handoff 136. Report cold and warm separately, and state the machine.
2. **Full run time:** a complete condition-B simulated run at n = 3,000 finishes in ≤ 3 minutes.
3. **No ranking regression:** on the 16 Set B reviews already in the scorecard (seed 1), per-review WSS@95 is within ±0.01 of the committed `015-setb-scorecard.json` for every review. If class balance is kept, mean WSS@95 must not drop. If SYNERGY data is available, mean WSS@95 must be ≥ 0.49 (validation 015 baseline 0.51).
4. **Largest-review feasibility:** run the 6 reviews with n > 6,000 end to end, or project n = 49k from measured scaling. Label the result `measured` or `projected` and say which. Target: a full run in ≤ 30 minutes for n = 49k.
5. **Unit tests:**
   - `createRanker(...).rank` and `rankRecords` give identical orders for the same inputs;
   - a warm-started ranker agrees with a cold fit on top-k order within a stated tolerance;
   - the ranker is deterministic across repeated calls.
6. **Gates:** lint, test and build are green, with only the known 12 baseline failures.

## Risk
If warm start or class balance shifts rankings, AC3 decides. Revert the change that causes the regression rather than loosening the bar. An exact speed-up, like handoff 137's, needs no AC3 re-run beyond the unchanged-order check.
