# Brief 016 — Living Review Updater L1: feed a review, verify the re-built search, rank what's new

**Date:** 2026-11-03
**Stage in pipeline:** Search + screening (folded into build order ④, search learning per field). Phase L1 of wiki `[[Living Review Updater]]`.
**Order:** after brief 015. The dev's lowest-numbered rule handles this.
**Blockers:** none. It uses the existing Gemini, PubMed, OpenAlex and EuropePMC keys. No new secrets and no schema change.

## Goal
A user gives Blindspot an existing systematic review (DOI or PMID). Blindspot:
1. reconstructs the review's **protocol**: question/PICO, eligibility criteria, search date, search strategy;
2. reconstructs its **included studies**;
3. re-runs a **re-built search** and **proves it** by measuring recall against the review's own includes;
4. returns the **new records published since the search date, ranked**, using the original includes as known positives.

L1 is stateless and backend-only. L2 (persistence, scheduling, digests) and L3 (re-pooling) are later briefs.

## Why
- Operator request (2026-11-03): turn any existing review into a living review. Living reviews are part of the mission, and manual upkeep is what makes them rare.
- **Edge:** every fed review is a built-in truth set (its includes). That makes the search **verifiable**, which a black-box index can't show. Each run is also field-labelled data for search learning (④) and the screening model (`[[Screening Model Plan]]`).

## Scope
**In**
1. `lib/living-review.ts`
   - **Resolve:** look up the review by DOI/PMID through the existing clients. Get OA full text via `resolveFulltext`, then JATS via `jatsToPages` where available. Fallback: title and abstract only.
   - **Protocol extraction (Gemini, one call):**
     - Returns `{ question, pico, eligibility, searchDate, databases[], strategyText|null, confidence }`.
     - **Every field cites its source:** a page/section excerpt pointer, never invented.
     - A missing field becomes `null` plus a reason, never a guess. In particular, no `searchDate` is guessed from the publication date: that falls back to `pubDate − 6 months`, labelled `assumed`.
   - **Included studies:**
     - From the reference section headed "included studies" or similar, or the characteristics-of-included-studies table, as `StudyId[]`.
     - Each carries `source: "heading" | "table" | "llm-classified" | "user"`.
     - Accept an optional user-supplied DOI/PMID list that **overrides** the extracted list.
     - Never treat the whole reference list as the includes.
   - **Re-built search:**
     - Translate the strategy, or build from PICO when the strategy is missing, into the existing PubMed, OpenAlex and EuropePMC query paths (`lib/boolean-search*.ts`, `lib/synonyms.ts`).
     - Record the exact query sent to each source (provenance).
   - **Search check:**
     - For includes published on or before `searchDate`, compute recall per source and union with `recall()` from `lib/recall-benchmark.ts` and `dedupeStudyIds`.
     - Return the **named missed includes**.
     - Verdict: `verified` (≥ 0.95, `RECALL_TARGET`), `partial` (0.80–0.95) or `failed` (< 0.80). **Below `verified`, the new-records list is still returned but labelled "search not verified".**
   - **New records:**
     - Re-run the search restricted to dates after `searchDate`.
     - Dedupe against the includes, including preprint→publication by DOI/PMID/title match.
     - Rank with `rankRecords`. Verdicts are the includes as positives plus pseudo-negatives: pre-`searchDate` retrieved records **not** in the includes, randomly sampled at most 5× the includes, tagged `approximate`.
     - Run `checkRetractions` over the original includes and attach the flags.
2. `app/api/living/route.ts`
   - POST `{ doi|pmid, includes?: string[] }` → `{ protocol, includes, search: { queries, recall, missed, verdict }, newRecords: ranked[], retractions, warnings[] }`.
   - Zod-validated, with the same auth and rate limiting as `/api/extract`, and a hard deadline (`AbortSignal.any`, as in handoff 126).
3. Tests use **synthetic** fixtures: tiny fake JATS, fake source responses. Cover:
   - include-section parsing;
   - user override wins;
   - search-date fallback is labelled `assumed`;
   - the recall verdict thresholds;
   - dedupe of a preprint and its publication;
   - pseudo-negatives never include an original include;
   - no network in unit tests.

**Out**
- UI: L1b, a design-track brief.
- Persistence and scheduled re-runs: L2. They reuse the `cron-search` / email-alerts path.
- PDF upload: the PDF path exists in `lib/extraction-pdf.ts`, but upload, storage and copyright handling get their own brief.
- Data extraction from the new studies; meta-analysis and re-pooling (L3, which needs the meta-analysis engine).
- Ovid/Embase-specific syntax beyond a best-effort translation. Any translated line that can't map is listed in `warnings`.

## Acceptance criteria (all `claimed` until the tester reruns)
1. **Real reviews.** Run the route on the two in-house truth-set reviews (Mitchell 2012, and the ketamine/TRD review from the field report, whose includes are already adjudicated) plus 3 OA reviews of the dev's choice. Use at least one Cochrane review if OA full text is available.

   For each, report in the handoff:
   - extracted vs actual number of includes;
   - the search-check recall per source and union;
   - the verdict;
   - the named missed includes;
   - the number of new records;
   - wall time.
2. **Include extraction accuracy:** across those 5 reviews, ≥ 90% of the actual includes are extracted and ≤ 10% of the extracted items are not includes. Where an OA include section is unavailable, say so; the user-override path must then work.
3. **No silent guessing:** every protocol field is either cited to a source excerpt or `null` with a reason. A unit test asserts that the schema rejects a non-null field without a citation.
4. **Honest verdict:** the response never presents new records as complete when the verdict is `partial`/`failed`. It carries a warning and the missed includes.
5. **Recall is the baseline we must improve:** state the mean union recall across the 5 reviews. This becomes the search-learning (④) baseline in the wiki.
6. **Hygiene:**
   - Abstract and full text are used in memory only.
   - Nothing from the reviews is committed except IDs and metrics in the handoff.
   - `npm run lint`, `npm test` and `npm run build` are green, with no failures beyond the known baseline.
7. **Latency:** p50 under 60 s per review on the dev machine, bounded by the hard deadline. Gemini calls per review: at most 3.

## Risks
- Strategies for MEDLINE via Ovid or Embase don't translate exactly. The search check is the safeguard, so don't weaken the thresholds.
- Paywalled reviews have no include section. The user override is the path, and the handoff says how often this happened.
- Pseudo-negatives are approximate (like Cochrane Set A). Never present them as human exclusions.
